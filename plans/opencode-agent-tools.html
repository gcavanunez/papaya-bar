Tools instead of JSON: Papaya as an opencode plugin

Follows the model picker (commit d41a627). This is the "agent tools" part of phase 5b in the sessions and groups plan; moving sync onto the library stays a separate plan. Everything marked proved was run on this Mac against your opencode 2.3.2, with a throwaway plugin in a scratch folder and nothing added to your config.

Today Smart group asks a model for JSON text and checks what comes back. With a small opencode plugin, the model calls Papaya's tools instead: each call is checked against a schema, Papaya answers over the connection it already has, and each call is a moment Papaya can show you.

Your three questions

"How could we move towards that dynamic? What would it take?"

Three pieces: a Papaya plugin for opencode (a new package in this repo, one line in your opencode config), a connection that stays open from opencode to Papaya, and Smart group rewritten as a short opencode session where the model calls a propose_group tool. Agent tools come after, on the same connection. Three phases.

"How exactly would we get the messages back?"

Papaya keeps one stream open: GET /api/event, filtered to Papaya's events. When the model calls a Papaya tool, the plugin puts the call on that stream and waits. Papaya does the work and answers with an ordinary request, POST /api/rpc/papaya/reply. In the spike the answer reached the model 18 ms after the call. Step by step.

"Show a glimpse of tool calls as they come back, not stacked up."

Yes. Every tool call raises events as it happens (started, called, done), so the panel can keep one line that changes with each call, plus a count. The spike's three groups arrived at 2.5, 2.9 and 3.0 seconds. Replay it.

1How messages travel

Two directions, two mechanisms, and nothing polls. Papaya to opencode is always an ordinary request with the pairing token, as Smart group does today. opencode to Papaya is always an event on a stream Papaya opened and keeps open. Here is one tool call, the agent asking for your tabs, with the timings the spike measured from the start of the run.

In the spike one Node script played both Papaya parts, so the hand-over between the offscreen page and the worker is the one step not yet run. The reply names the location the call came from (?location[directory]=…), because the plugin runs once per opencode folder.

Why an offscreen page holds the stream

Chrome stops an extension's background worker after 30 seconds without events, and also when a fetch response takes longer than 30 seconds. Only WebSockets keep it alive, and opencode's event stream is Server-Sent Events. Papaya already has an offscreen page (for copying to the clipboard); it can hold the stream for as long as Chrome runs and pass each call to the worker, which a message wakes. The browser's EventSource can't send the pairing token, so the page reads the stream with fetch, as the spike did.

The stream is volatile by opencode's contract: events sent while it's disconnected are lost. So Papaya reconnects with a back-off and tells the plugin it's there every 20 seconds, and a tool with no Papaya listening fails at once with "Papaya isn't connected" rather than waiting out its 20-second timeout.

3Smart group as tool calls

Today
  1. One request to /api/experimental/generate/text with every tab and the instructions.
  2. The model writes JSON as text.
  3. Papaya digs the JSON out, checks every tab number, asks once more if it isn't JSON, then falls back and says why.
  4. Nothing to show until the whole reply arrives.
With the plugin
  1. Papaya starts a short session with the model you picked, allowed only Papaya's tools, and sends the numbered tabs.
  2. The model calls papaya_propose_group({name, tabs}) once per group. opencode checks each call against the schema.
  3. The plugin also checks the numbers exist and aren't taken; a bad call gets an error the model sees and fixes, instead of failing the run.
  4. Papaya reads each group from its session.tool.called event as it lands, shows it, and deletes the session at the end. Cancel stops the session.

Smart group doesn't need the relay at all: the tab list goes in the prompt and the groups come back as events, so only propose_group has to exist on the opencode side. Today's path stays as the fallback when the plugin isn't installed, followed by the on-device model and grouping by site, as now.

    6What it takes

    1. Phase A The connection

      • A new package, apps/opencode-plugin (plugin id papaya): the RPC contract (hello, reply, the call event), a helper that registers a relayed tool with its waiting calls and timeouts, and the "Papaya isn't connected" check.
      • Installing it: one line in ~/.config/opencode/opencode.jsonc, "plugins": [".../apps/opencode-plugin"]. opencode reloads it on save.
      • In Papaya, the offscreen page reads /api/event, reconnects with a back-off, says hello every 20 seconds, and passes calls to the worker.
      • Settings shows whether the plugin is installed and connected.
      Done when a test tool called from a real opencode session gets its answer from the real extension, still works after Chrome has idled for an hour, and recovers by itself after opencode restarts.

    2. Phase B Smart group as tool calls

      • papaya_propose_group with its checks, and the short session per run (model from the picker, only Papaya's tools, deleted after).
      • The live line and count in the panel; Cancel stops the session.
      • The fallback chain when the plugin is missing: today's JSON request, then on-device, then by site.
      Done when 200 real tabs group through tool calls with the line moving throughout, and a deliberately bad call (a tab number that doesn't exist) is corrected by the model instead of failing the run.

    3. Phase C Tools for your agents

      • C1: the two read-only tools, the skill, and the Settings switch (off by default).
      • C2: the tools that act, each with Papaya's Undo, the toolbar badge and the panel line; switching and closing ask first.
      Done when in an ordinary opencode session, "group my Lisbon tabs" works end to end and shows up in Papaya with an Undo.

    8Risks

    RiskWhat we'd do
    opencode's plugin API is new The spike already hit one bug. Pin the opencode version the plugin is tested with, keep the JSON fallback, and have Settings say when the plugin and opencode don't match.
    Missed events The stream drops events while disconnected. Papaya reconnects; the plugin's hello check and timeout give the agent a clear error instead of a hang.
    The offscreen page's reason Chrome asks why an offscreen page exists; Papaya's says "clipboard". Fine for an unpacked extension, but a Web Store listing could question a page kept open for a connection.
    Who can answer a call Anything holding a pairing token can call papaya.reply. The plugin only accepts replies for calls it's waiting on, by an unguessable id.
    What agents can see Tab titles and addresses. Off by default, a switch in Settings, and the acting tools show in Papaya with Undo.
    Cost and speed Tool calls carry the tools' descriptions, so a run costs a little more than one JSON reply: still fractions of a cent with Haiku 5.5. The spike took 3.8 s for 10 tabs.
