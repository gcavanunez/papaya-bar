Problem — the browser seam doesn't exist: chrome.* leaks into 9 caller files, and helpers.ts is shallow (its interface nearly matches its implementation — closeTab is chrome.tabs.remove plus a loop).

  • Deletes 5 duplicate "activate tab" implementations
Evidence the seam is real: rendering the UI outside Chrome already required a hand-written chrome shim (this session's visual tests). Two adapters — real chrome, in-memory fake — is exactly the "real seam" test.

Problem — the hairiest implementation in the app (window/display fitting, URL-keyed regrouping) is duplicated; UI Session restores run one copy, background Context swaps run the other, and the capture helpers are a line-for-line copy that doesn't even import its twin.

Solution — deepen swapEngine into the single restore engine; openAll and useContexts delegate through its interface and the copies are deleted.

  • Deletion test passes: complexity concentrates
  • Locality: restore bugs fixed once
  • One interface to test (with C1's fake adapter)
  • Fixes land on both swap paths at once

Problem — a Session lives in two stores with unlinked IDs; saves write both, deletes touch one. The migration path even reads localStorage while the live path writes chrome.storage.local — the seams have drifted apart.

Solution — a Sessions module with one interface; TinyBase becomes the canonical adapter, the legacy Map demotes to a read-only migration adapter and then gets deleted.

  • Kills a data-integrity bug class
  • Locality: persistence knowledge in one module
  • Two adapters justify the seam (canonical + migration)
  • Also deletes 5 dead store.ts exports en route

4 · The Mirror protocol: give the worker seam a single owner

Worth exploring ports & adapters

src/lib/contextBridge.ts · background.js · src/content/index.ts · src/hooks/useContexts.ts

Before — protocol knowledge in 4 files

contextBridge.ts types + keys (canonical)
background.js re-declared keys · untyped op literals · mirror shape by convention
content/index.ts re-declared Model shape · message strings
useContexts.ts op-queue drain semantics · parkQueue (third untyped key)

After — one protocol module, two adapters

context bridge

Mirror + StoreOp + parkQueue: encode · decode · enqueue · drain

page adapter (TinyBase) worker adapter (storage.local)

background becomes TS (or imports a built protocol module) so ops are constructed through the interface, not by string convention

Problem — the page↔worker seam is real (two runtimes, one storage key), but its interface is folklore: background.js builds StoreOps as untyped literals against a TypeScript type it cannot import; a shape change breaks silently at runtime.

Solution — deepen contextBridge into the protocol's single owner; both runtimes consume it as adapters at the seam.

  • Locality: protocol changes in one module
  • Type safety crosses the worker seam
  • Two adapters — the seam is already real
  • Protocol becomes testable round-trip

Problem — the derivation pipeline (domain grouping → history window → search + filters → flat order) and the cursor/visual model are pure logic trapped inside one 2,300-line implementation; every bug fix is verified by hand.

Solution — keep the component's external interface; give the implementation two internal seams: a tab query module and a cursor + selection module.

  • Pure interface = trivial tests (dedupe, presets, counts)
  • Keymap bindings bind to modules, not refs
  • Locality: filter bugs stop hiding in the template
  • Matches tech-debt-todos item 11

Top recommendation

1 · The tab workspace module

It's the enabling seam for everything else in a repo with zero tests: the in-memory adapter it creates is the same one candidates 2, 3, and 5 need to become testable, and the shim we hand-wrote just to render the UI proves the second adapter is real demand, not speculation.
